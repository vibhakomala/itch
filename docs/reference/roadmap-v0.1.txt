1. Executive Product Definition
ITCH is an open tangible-computing toolkit that lets a child or learner manipulate physical pieces, drawings, and eventually physical code blocks in a camera-visible workspace and use those actions as inputs to interactive Scratch projects. The initial reference experience runs sensing, recognition, the ITCH scene model, and Scratch playback on the same tablet or phone. A remote-phone provider remains a supported later deployment mode but is not part of the core execution path.
1.1 Product principles
Open first: file formats, protocols, tangible specifications, calibration assets, and reference hardware should be openly documented and remixable.
Local first: the core experience must work without a cloud vision service and should not require images to leave the device.
Low-cost fabrication: paper/cardboard must be a valid entry-level tangible medium; 3D printing and laser cutting are enhancements, not requirements.
Scratch-native semantics: Scratch creators should consume meaningful concepts such as “current word”, “piece present?”, and “when scene changes”, not computer-vision jargon.
Determinism before ML: use calibration geometry, fiducials, piece design, and constrained classifiers before introducing larger general-purpose models.
Provider separation: camera/recognition is independent of Scratch. Scratch is one consumer of the scene model.
Progressive capability: V0 letters/numbers → V1 drawings → V2 physical code blocks; each version must remain usable independently.
Child-safe by default: no face recognition, no identity tracking, no cloud image retention, and clear camera-use indicators.

1.3 Product success metrics
First-time setup: a new user can open a compatible project, allow camera access, place the mirror jig/calibration mat, and reach a working state without developer tools.
Interaction latency: physical change to Scratch-observable state should feel immediate; target median ≤150 ms for V0 local mode and hard acceptance ≤250 ms on the baseline device.
Recognition: V0 target ≥99% piece identity accuracy under supported lighting and ≥98% scene-state accuracy across the acceptance test set.
Robustness: no false “add/remove” event from a single bad frame; scene events must be temporally stabilized.
Portability: reference implementation works on at least one current iPad-class device and one current Android tablet/phone browser before V0 public release.
Community: all tangible-pack definitions, calibration assets, and starter projects are documented enough for an external contributor to create a new pack without modifying the vision core.
2. Reference Architecture
B2 is the reference architecture. Recognition is implemented as a reusable JavaScript/TypeScript library inside the same page/application environment as the Scratch runtime, but it remains logically separate from the Scratch extension. This preserves standalone play while keeping the engine reusable outside Scratch.

2.2 Scene model — initial contract
type TangibleId = string;interface TangibleObject {  trackId: string;          // ephemeral stable ID while object remains visible  pieceId: TangibleId;      // semantic ID, e.g. "letter:A"  packId: string;           // e.g. "itch.alphanumeric.v0"  x: number;                // normalized workspace coordinate [0,1]  y: number;  rotationDeg: number;  confidence: number;       // [0,1]  bbox?: {x:number; y:number; w:number; h:number};}interface TangibleScene {  revision: number;  timestampMs: number;  workspaceStatus: "uncalibrated" | "calibrating" | "ready" | "degraded";  objects: TangibleObject[];  rows?: string[][];  derived?: Record<string, unknown>; // e.g. currentWord}
The scene model is the primary compatibility boundary. Camera implementation, classifier, Scratch version, and hardware jig may evolve independently as long as this contract is preserved or versioned explicitly.
2.3 TangiblesProvider contract
interface TangiblesProvider {  start(): Promise<void>;  stop(): Promise<void>;  getScene(): TangibleScene;  onSceneChanged(cb: (scene:TangibleScene) => void): Unsubscribe;  onObjectAdded(cb: (object:TangibleObject) => void): Unsubscribe;  onObjectRemoved(cb: (object:TangibleObject) => void): Unsubscribe;  getStatus(): ProviderStatus;}
LocalTangiblesProvider is the Phase 2/3 implementation. RemoteTangiblesProvider is later and must satisfy the same contract.

4. Development Workflow and Quality Gates
Every phase produces runnable output and test evidence. A phase is not complete because code exists; it is complete only when its exit gate passes. Issues and commits should reference requirement/test IDs where practical.
4.1 Recommended repository structure
itch/├── packages/│   ├── core/│   ├── vision/│   ├── scratch/│   ├── packs/│   └── devtools/├── hardware/│   ├── jig/│   └── workspace/├── fixtures/│   ├── recorded-video/│   └── expected-scenes/├── examples/│   └── scratch/├── docs/│   ├── architecture/│   ├── protocol/│   └── contributing/└── tools/
4.2 Engineering practices
TypeScript for public packages; strict type checking enabled.
Unit tests for scene logic and pack parsing; deterministic frame/fixture tests for vision.
Golden-fixture regression tests: recorded frame sequence + expected scene timeline.
Performance benchmark script that reports capture FPS, processing FPS, median/p95 latency, CPU time if available, and dropped frames.
Feature flags for experimental recognizers so Scratch-facing API remains stable.
Architecture Decision Records (ADRs) for irreversible or cross-package choices such as marker family, classifier type, and Scratch distribution strategy.
No requirement to fork Scratch until the smallest possible external/custom-extension path has been validated; if a fork is required for distribution, isolate the delta.

Phase 1 — Workspace Optics, Calibration, and Rectification
Phase objective. Make arbitrary supported phone/tablet+jig geometry look like the same canonical A5 workspace to the recognition engine.
Outputs
A5 calibration mat v0.1 (printable PDF/SVG)
Four-corner/fiducial detection
Homography calculation and rectified canonical image
Calibration quality score and failure states
Adjustable mirror-jig prototype and dimensions
Calibration/debug overlay
Calibration fixture dataset across angles/lighting
Implementation details
Define a canonical workspace pixel size independent of capture resolution; initial recommendation 840×592 or equivalent 10:7 ratio matching A5 landscape. Keep internal coordinates normalized.
Use four high-contrast fiducials near workspace corners. Marker family is an ADR: simple custom corner marks may suffice; ArUco/AprilTag-like markers are candidates if licensing/implementation footprint is acceptable.
Estimate homography from detected corner points. Reject calibration if quadrilateral geometry is implausible, too small in frame, severely skewed, or markers are ambiguous.
Apply mirror compensation once in the camera transform so downstream scene coordinates remain intuitive (left on mat = left in scene).
Calibration should persist for a session but continuously verify drift at low cost. Do not recompute full setup every frame unless needed.

Phase 8 — V2 Physical Code Blocks
Phase objective. Interpret machine-identifiable physical blocks as a constrained executable program, then progressively map them to Scratch semantics.
V2 staged grammar
Stage
Grammar
Examples/notes
V2.0
Linear commands
move, turn, say, wait; numeric parameter tiles
V2.1
Event caps
when green flag, when sprite clicked
V2.2
Control nesting
repeat, forever, if; C-shaped or spatial nesting
V2.3
Reporters/booleans
limited expression grammar
V2.4
Optional Scratch block materialization
generate actual Scratch block stacks if technically justified

Implementation details
Code tiles should carry deterministic machine identity; OCR of printed Scratch text is not the primary recognition mechanism.
The scene parser converts spatial relationships into an intermediate representation (IR) independent of Scratch block XML/internal serialization.
Interpreter-first strategy: execute the IR through ITCH/Scratch adapter before attempting to programmatically mutate the Scratch workspace.
Physical grammar should make invalid syntax visible and recoverable. Parser returns structured errors (e.g., unattached parameter, unmatched control block, ambiguous nesting).
Only after the IR/interpreter is stable should the team evaluate whether generating actual Scratch blocks materially improves learning/product value.

8. Test Strategy
8.1 Test pyramid
Unit: scene types, row grouping, temporal stabilization, tracking association helpers, schemas, parser.
Fixture regression: deterministic recorded frames/images → expected detections/scenes/events.
Integration: LocalTangiblesProvider → @itch/scratch reporters/hats using mocked and replayed scenes.
Device/browser: camera lifecycle, performance, orientation, permissions, thermal behavior.
Hardware acceptance: jig fit, calibration, shadows/glare, mirror variants.
Child/user testing: setup comprehension, manipulation behavior, accidental occlusion, perceived latency, delight/frustration points.
8.2 Canonical fixture format
fixtures/<case>/├── metadata.json        # device/camera/lighting/pack├── frames/ or video     # deterministic source├── expected-scenes.json # scene timeline / tolerances└── notes.md             # known edge cases
Vision outputs often require tolerances rather than exact pixel equality. Tests should compare semantic identity exactly and pose/geometry within documented tolerances. Event timelines should be compared after the same stabilization settings used in production.

10. Security, Privacy, and Child-Safety Baseline
Camera permission must be explicit and controlled by browser/platform permission mechanisms.
Local mode processes camera data in memory on-device; no default upload, analytics video capture, or image retention.
Fixture recording is a developer action and should clearly indicate that images/video are being saved.
No biometric identification, face recognition, emotion inference, or persistent person tracking is part of ITCH.
Remote mode pairs explicitly and should transmit scene semantics by default. If a future debugging mode streams video, it must be visibly opt-in.
Published examples should avoid requiring personal identifiers or student accounts to use tangible interaction.
11. Definition of “MVP”
ITCH MVP is intentionally narrower than “full alphabet recognition.” The product hypothesis is validated when all of the following are true:
A tablet/phone running the ITCH-enabled Scratch environment uses its own front camera through a simple mirror jig.
The A5 mat automatically calibrates and rectifies.
At least six physical tiles can be recognized, located, and tracked robustly.
@itch/core produces a stabilized scene and current-word derivation.
Scratch receives that state through @itch/scratch and runs a child-visible interaction.
The full loop works locally, without a companion computer or cloud vision service.
Recorded fixtures reproduce the semantic behavior deterministically.
Measured performance and accuracy meet the Phase 2/3 gates on the baseline device.
Only after this MVP gate should the team invest substantially in 36-class recognition, remote pairing, semantic drawing recognition, or physical Scratch-program materialization.

13. Change Control for This Roadmap
This document is intended to be referenced throughout implementation. Changes should preserve IDs whenever possible. If a requirement is removed, mark it deprecated rather than reusing the identifier. New requirements receive new IDs. Suggested versioning:
v0.x — architecture/prototype period; requirements can evolve with ADRs.
v1.0 — V0 public-release baseline; compatibility commitments begin.
Minor roadmap revision — clarifications, new tests, backlog refinement.
Major roadmap revision — scene/API incompatibility, scope reset, or fundamental architecture change.
When discussing development, use references such as “implement P1-002”, “T-P2-05 is failing on Android”, or “ADR-004 selected deterministic tile IDs”. This makes the roadmap operational rather than descriptive.
